# SA7 interpretation and maintainability note

The approved bounded workflow is endpoint registration → scheduled check → result capture → human incident acknowledgement → verified recovery → reporting. The prototype uses Flutter Web for the required browser client, FastAPI for the application contract, a separate APScheduler worker for unattended checks, and the user's selected MySQL database.

**Observed facts:** the backend's original timestamp failure was reproduced and corrected with MySQL microsecond UTC storage. The passing MySQL-backed regression has 30 cases; a later API-documentation/auth adjustment passed its focused checks. The final Flutter regression has ten cases, including a dialog kept open while monitoring state changes. Earlier diagnostic artifacts preserve failed checks and their corrections, with secrets removed. Real HTTP evidence demonstrates normal success, a 503 recovered by retry, retry exhaustion routed to support, idempotent resubmission, acknowledgement and verified recovery. Actual worker-process evidence demonstrates scheduled execution and restart without browser dependence. Browser evidence and its expected/actual records are indexed separately rather than inferred from widget tests.

**Reasoned interpretation:** bounded retry recovers short-lived dependency faults while limiting work during a persistent outage. Acknowledgement records ownership but cannot manufacture a healthy result. Two successful cycles provide a small recovery verification threshold; they do not prove future availability. A database-scoped execution lock and submission key address overlap and replay as distinct problems. Transactional in-app notifications make the human-action and recovery signal inspectable without an external messaging dependency.

Interval scheduling fits a service that may fail without emitting an event. A browser timer cannot supply unattended monitoring, while a distributed queue adds operational components beyond this student boundary. A single worker is easier to explain and maintain but has finite sequential throughput; this is a documented tradeoff rather than a scalability claim.

The system retains status, timestamps, bounded errors and elapsed time instead of service bodies or credentials. Configuration examples contain no secrets. The shared local operator capability is a proportional SA7 control, and individual authentication, RBAC and HTTPS remain Week 14 work. Observed uptime measures successful completed checks, not time-weighted SLA availability.

**Recommendation:** suitable for a controlled Week 13 demonstration using the saved passing evidence and fictional approved services. Student reproduction, contribution reflection and instructor acceptance are still required. Production exposure should await the later security, performance, deployment/recovery and UAT assessments. Maintenance priorities are reviewed dependency updates, explicit schema migrations, retention/log rotation, watchdog behavior and backup/restore verification; operational owners and triggers are in `maintainability.md`.
